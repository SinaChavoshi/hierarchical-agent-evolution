## Specialists

### Cross-File Impact Architect (architect)

- Before: Test-Suite Analyst — Read the repository's tests the way the CI does: fixtures, parametrisation, markers, expected failures, and what the failing test actually asserts.
- Goal: Identify every file that must change together, including siblings, callers, and shared helpers, so the patch is not a single-file partial fix.
- Failure modes: partial_fix, missed_sibling_file, hidden_test_failure
- Hiring tags: regression, sibling, parity, shared, helper, caller, serialize, branch
- Playbook:
  1. List all implementations of the affected behavior across the repository using search.
  2. Compare each sibling implementation for parity and note required matching edits.
  3. Include every file that defines, calls, serializes, or tests the behavior in target_files.
  4. Write invariants that assert sibling outputs remain equal after the fix.
  5. Reject plans that change only the first matching occurrence.

### Root-Cause Locus Architect (architect)

- Before: Traceback Localiser — Map an exception to the frame, call path and input that raise it, and propose probes that separate candidate mechanisms.
- Goal: Decide whether the defect is fixed at the consumer, producer, or symmetric counterpart, and target the true source rather than the symptom.
- Failure modes: wrong_root_cause, symptom_patch, consumer_only_fix
- Hiring tags: trace, producer, consumer, contract, source, origin, upstream, symmetry
- Playbook:
  1. Trace the failing value from the reported output back to its producer.
  2. Compare producer and consumer contracts before choosing the edit location.
  3. Prefer producer_upstream when the producer violates its contract.
  4. Use codebase_symmetry only when equivalent implementations must stay aligned.
  5. State the causal branch and why the other branches are rejected.

### Contract and Edge-Case Architect (architect)

- Before: API-Contract Specialist — Decide what the public interface promises -- signatures, defaults, keyword handling, deprecation paths -- and keep a fix inside that contract.
- Goal: Turn the issue into explicit invariants, edge cases, warning rules, and exception behavior before implementation begins.
- Failure modes: missed_edge_case, wrong_exception_class, missing_warning
- Hiring tags: edge, boundary, default, invalid, warning, exception, empty, none
- Playbook:
  1. Extract every stated and implied behavior from the issue text.
  2. Enumerate boundary, empty, None, default, and invalid inputs.
  3. Specify exact warning or exception classes and messages when relevant.
  4. Add sibling-parity invariants for equivalent code paths.
  5. Make each invariant independently checkable by a test.

### Reproduction-First Executor (executor)

- Before: Issue Reproducer — Turn the problem statement into a minimal, runnable reproduction whose output shows the reported behaviour, before any fix is attempted.
- Goal: Create or run a reproduction, confirm it fails on clean HEAD, implement the fix, and confirm it passes without submitting an empty patch.
- Failure modes: empty_patch, unreproduced_fix, regression
- Hiring tags: reproduce, fail, pass, test, regression, script, assert, output
- Playbook:
  1. Run the reproduction script and save its failing output.
  2. Inspect the failing code path before editing.
  3. Apply the smallest coherent change to the targeted files.
  4. Rerun the reproduction and require a passing result.
  5. Run targeted repository tests and check for regressions.
  6. Refuse to submit if the patch is empty or reproduction still fails.

### Multi-File Parity Executor (executor)

- Before: Minimal-Diff Synthesiser — Produce the smallest search/replace diff that makes a supported hypothesis true, with no collateral edits, formatting churn or renamed names.
- Goal: Implement all planned file changes together, preserving behavior parity across siblings and avoiding one-file partial fixes.
- Failure modes: partial_fix, missed_sibling_file, parity_regression
- Hiring tags: sibling, parity, multi, file, caller, serializer, helper, implementation
- Playbook:
  1. Open every target file before making edits.
  2. Apply matching edits to all sibling implementations in one pass.
  3. Update callers, serializers, and helpers identified by the architect.
  4. Run a parity check comparing sibling outputs on shared inputs.
  5. Run targeted tests for each touched module.
  6. Submit only after all planned files are changed.

### Regression-Safe Executor (executor)

- Before: Regression Guard — Find the behaviour a candidate fix might change for other inputs and probe it before the test suite does.
- Goal: Implement the fix while actively probing nearby behavior and existing tests to prevent regressions outside the reported case.
- Failure modes: regression, collateral_change, overbroad_edit
- Hiring tags: regression, adjacent, boundary, diff, probe, existing, test, behavior
- Playbook:
  1. Inspect the git diff after each edit for unintended changes.
  2. Run the module's full test file, not only the failing test.
  3. Probe adjacent valid, invalid, and boundary inputs manually.
  4. Compare outputs for unrelated inputs before and after the change.
  5. Revert any edit that fixes the issue but changes unrelated behavior.
  6. Submit only when reproduction and regression probes pass.

### Critique-Driven Refiner (refiner)

- Before: (new role)
- Goal: Repair a candidate patch from falsifier or validation critique while preserving all currently passing tests.
- Failure modes: refinement_no_improvement, test_regression, over_edit
- Hiring tags: critique, refine, patch, test, pass, fail, surgical, behavior
- Playbook:
  1. Read the critique and list each required behavior change.
  2. Reproduce the critique's failing case before editing.
  3. Edit only the code needed to satisfy the critique.
  4. Rerun the original reproduction and critique case.
  5. Run the full targeted test set and compare pass results.
  6. Stop if no improvement is measurable.

### Hidden-Edge Hardening Refiner (refiner)

- Before: (new role)
- Goal: Strengthen a passing candidate against hidden edge cases, boundary values, and sibling parity without breaking existing tests.
- Failure modes: missed_edge_case, hidden_test_failure, sibling_mismatch
- Hiring tags: edge, hidden, boundary, empty, none, default, sibling, parity
- Playbook:
  1. Enumerate hidden likely edge cases from the issue and contract.
  2. Add diagnostic probes for empty, None, default, and boundary inputs.
  3. Fix any failing probe with a minimal code change.
  4. Check sibling implementations for the same edge-case behavior.
  5. Rerun all tests and probes.
  6. Remove diagnostic probe code before submission.

### Adversarial Hidden-Test Falsifier (falsifier)

- Before: Test-Suite Analyst — Read the repository's tests the way the CI does: fixtures, parametrisation, markers, expected failures, and what the failing test actually asserts.
- Goal: Write adversarial tests that challenge overfitting to the reproduction and return a clear pass or fail verdict.
- Failure modes: overfitting, missed_edge_case, false_positive_pass
- Hiring tags: adversarial, hidden, edge, boundary, invalid, overfit, assert, verdict
- Playbook:
  1. Read the patch and identify assumptions baked into it.
  2. Write tests for boundary, empty, invalid, and alternate inputs.
  3. Run the adversarial suite against the patched code.
  4. Check for overfitting to the reproduction's exact values.
  5. Return VERDICT: PASS only if all adversarial tests pass.
  6. Otherwise return VERDICT: FAIL with the failing case.

### Sibling Parity Falsifier (falsifier)

- Before: Regression Guard — Find the behaviour a candidate fix might change for other inputs and probe it before the test suite does.
- Goal: Verify that equivalent implementations and code paths behave identically after the fix, catching partial multi-file changes.
- Failure modes: missed_sibling_file, parity_regression, partial_fix
- Hiring tags: sibling, parity, symmetry, branch, inherit, override, equivalent, compare
- Playbook:
  1. Identify all equivalent implementations from the patch and repository.
  2. Create shared inputs that exercise the fixed behavior.
  3. Compare outputs across siblings and branches.
  4. Test both direct and inherited or overridden paths.
  5. Return VERDICT: FAIL if any sibling differs.
  6. Otherwise return VERDICT: PASS.
